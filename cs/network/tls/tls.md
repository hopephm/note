## 🔒 TLS (Transport Layer Security)

**TLS란?**

> 클라이언트와 서버 간 통신 내용을 암호화하여 도청/위변조를 방지하는 보안 프로토콜
>
- TCP 위에서 동작 (애플리케이션 계층 보안)
- 암호화, 무결성, 인증 제공

---

### 📜 인증서 구조

**X.509 인증서에 포함된 주요 정보**

| 항목 | 설명 |
| --- | --- |
| Subject | 인증서 주체 (서버의 도메인 등) |
| Issuer | 인증서 발급자 (CA) |
| Public Key | 서버의 공개키 |
| Signature | CA가 서명한 인증서 본문 해시 |
| Validity | 유효 기간 |
| Algorithm | 사용된 서명 알고리즘 (예: SHA-256) |

---

### 🔐 공개키 암호화 기초

| 구분 | 설명 |
| --- | --- |
| 공개키 | 모두가 알 수 있음. 암호화 또는 검증에 사용 |
| 개인키 | 소유자만 가짐. 복호화 또는 서명에 사용 |
| 암호화 방식 | 공개키로 암호화 → 개인키로 복호화 |
| 서명 방식 | 개인키로 서명 → 공개키로 검증 |

---

### 🧾 TLS 인증서 검증 흐름

**서버 인증서 발급 과정**

1. `certInfo` = 서버 정보(도메인, 공개키, 유효기간 등)를 포함한 인증서 데이터
2. `hashInfo` = `certInfo` 본문을 특정 해시 알고리즘(SHA-256 등)으로 해싱
3. `signature` = 서버(또는 CA)의 **개인키**로 `hashInfo`를 암호화해 서명 생성
4. `signature`를 포함해 인증서(공개키 + 본문 + 서명) 완성 및 발급

**클라이언트의 인증서 신뢰 여부 판단 과정**

1. `cert` = 서버로부터 받은 인증서 (본문 + `signature`)
2. 클라이언트가 인증서 내 서명 알고리즘으로 `cert` 본문(서명을 제외한 부분)을 해싱 → `clientHash` 생성
3. `signature`를 클라이언트가 신뢰하는 CA의 **공개키**로 복호화 → `serverHash` 추출
4. `clientHash`와 `serverHash`가 일치하면 서명 검증 성공 → 인증서 신뢰 가능
5. 여러 CA가 있는 경우 위 과정을 반복하며 검증

---

### 🏗️ CA 인증서 발급 흐름

**CA → 하위 인증서 발급**

- 하위 인증서의 본문을 CA가 해싱
- 해시값을 **CA의 개인키**로 암호화 → Signature 생성
- 서명된 인증서 전달 → 상위 CA의 서명 체인으로 클라이언트 신뢰 획득

📝 모든 하위 인증서 검증은 결국 CA의 신뢰 루트로 연결됨

---

### 📁 TLS 인증서 파일 종류 (예시: Kubernetes)

| 파일 | 설명 |
| --- | --- |
| `ca.crt` | 루트 인증서 (CA의 공개키 포함) |
| `tls.crt` | 서버의 인증서 (공개키 포함, CA 서명) |
| `tls.key` | 서버의 개인키 (절대 외부 공개 X) |

---

### 🧠 기억 포인트

- 인증은 신뢰 체인 + 서명 검증
- 암호화는 대칭키, 인증은 비대칭키
- 클라이언트는 공개키만으로도 검증이 가능
- 해싱 알고리즘 정보는 인증서 내부에 있음
