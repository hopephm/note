## 💬 NFC vs NFD 정규화 개념 정리

---

### 🖼️ 정규화 차이가 발생하는 배경

유니코드(Unicode)는 같은 문자를 **여러 코드 포인트 조합으로 표현할 수 있도록 설계**되어 있다.  
예를 들어 `é` 문자는 단일 코드포인트 `U+00E9`(조합형)로도, `'e' (U+0065)` + `́ (U+0301)`(분해형) 조합으로도 표현 가능하다.

이처럼 **시각적으로 동일하지만 내부 코드 시퀀스가 다른 표현이 존재**하기 때문에,  
운영체제·입력기·파일시스템·브라우저 등 환경마다 서로 다른 정규화 형태(NFC/NFD)를 사용할 수 있다.

예시:
| 환경 | 기본 정규화 형태 |
|------|----------------|
| **Windows / Linux** | NFC (Composed Form) |
| **macOS (HFS+, APFS)** | NFD (Decomposed Form) |
| **웹 브라우저 / 대부분의 언어 런타임** | NFC 기준 처리 |

따라서 서로 다른 환경에서 생성된 문자열을 그대로 비교하거나 S3 등의 바이트 단위 저장소에 저장하면,  
**눈에 보이기엔 같지만 내부적으로는 다른 바이트열**이 되어 충돌이나 테스트 오류가 발생할 수 있다.

---

### 🍉 NFC와 NFD의 정의

| 구분 | 정식 명칭 | 변환 과정 | 코드 포인트 예시 (`é`) | UTF-8 바이트 |
|------|------------|------------|------------------------|----------------|
| **NFC** | Normalization Form C (Canonical Composition) | 분해 가능한 문자를 가능한 한 **합성** | U+00E9 | `0xC3 0xA9` |
| **NFD** | Normalization Form D (Canonical Decomposition) | 문자를 가능한 한 **분해** | U+0065 U+0301 | `0x65 0xCC 0x81` |

정규화는 유니코드 표준 [UAX #15 (Unicode Normalization Forms)](https://unicode.org/reports/tr15/) 에 정의되어 있으며,  
모든 유니코드 문자열은 NFC/NFD 중 하나로 정규화 가능하다.

수식 형태로 표현하면 다음과 같다:
- **NFD(s)** = `canonical_decompose(s)`
- **NFC(s)** = `canonical_compose(NFD(s))`

---

### 🤐 발생할 수 있는 실무 이슈

> **한줄 요약:**  
> 같은 한글도 내부적으로 NFC/NFD로 표현 가능하며,  
> S3 key는 바이트 단위로 비교되므로  
> 모든 로직이 NFC 기준으로 동작하는 상황에서  
> macOS에서 업로드된 NFD 문자열은 S3 key 불일치로 테스트 오류를 유발할 수 있다.

**구체적 메커니즘**
- S3 오브젝트 키(Object Key)는 **UTF-8 바이트 시퀀스 그대로 저장**된다.
- 즉, 시각적으로 동일한 문자열이라도 NFC/NFD에 따라 **서로 다른 바이트열**로 인코딩된다.
- 내부 로직이 NFC 기준으로 구현되어 있으면,  
  macOS 클라이언트가 **NFD로 업로드한 파일명**은 서버에서 NFC 키와 매칭되지 않아 `404`, `NoSuchKey`, 또는 테스트 불일치 발생.

**예시**
```text
입력 문자열: "한글"
NFC  → [U+D55C, U+AE00]
NFD  → [U+1112, U+1161, U+11AB, U+1100, U+1173, U+11AF]
→ 서로 다른 UTF-8 바이트 시퀀스 → 서로 다른 S3 object key
