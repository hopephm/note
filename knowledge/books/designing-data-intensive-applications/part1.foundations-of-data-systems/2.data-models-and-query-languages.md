## 2. 데이터 모델과 질의 언어 ✅

---

### 💬 데이터 모델의 중요성
- 데이터 모델에 따라 애플리케이션이 할 수 있는 일과 없는 일이 달라지므로 **선택이 중요**함

---

### 💬 데이터 모델 비교

#### 1️⃣ 관계형 모델 (Relational Model)
- **정의**: 데이터를 테이블(관계) 형태로 구조화하고, 기본 키(PK)와 외래 키(FK)를 통해 각 테이블 간 관계를 명시적으로 정의하여 관리
- **장점**
    - **데이터 무결성 보장**: PK, FK, 제약조건 등을 통해 데이터 일관성 유지
    - **추상적 개념 명시 가능**: 테이블, 스키마, 관계를 통해 현실 세계 모델링 용이
    - **표준화된 쿼리 언어**: SQL로 CRUD, 복잡한 조회, 집계, 조인 가능
    - **ACID 트랜잭션 지원**: 원자성, 일관성, 격리성, 지속성 보장
    - **데이터 독립성**: 물리적 저장과 논리 구조 분리 가능
    - **보편적 도구 및 생태계**: 다양한 DBMS, ORM, 관리 도구 지원
- **단점**
    - **확장성 제한**: 수평 확장(sharding) 어려움, 대규모 분산 처리 부담
    - **유연성 부족**: 스키마 변경 시 마이그레이션 필요 → 비정형 데이터 처리 어려움
    - **성능 문제**: 복잡한 조인과 트랜잭션이 많을 경우 성능 저하
    - **비정형 데이터 처리 제한**: JSON, 배열, 로그, 이벤트 데이터 처리에 적합하지 않음
    - **운영 복잡도**: 큰 테이블, 복잡한 제약조건, 인덱스 관리 필요

#### 2️⃣ 도큐먼트 모델 (Document Model)
- **정의**: 데이터를 도큐먼트 단위(JSON, BSON 등)로 저장하고, 도큐먼트 내부 구조를 자유롭게 정의하며 컬렉션 단위로 관리
- **장점**
    - **비정형 데이터 처리 용이**: JSON/BSON 등 자유로운 구조 → 스키마 사전 정의 불필요
    - **유연한 스키마**: 도큐먼트 단위로 구조 다르게 정의 가능, 필요 시 필드 추가/삭제 용이
    - **복잡한 조인 최소화**: 관련 데이터를 한 도큐먼트에 포함시키면 조인 없이 조회 가능
    - **확장성 용이**: 수평적 확장(sharding)과 분산 저장에 유리
    - **빠른 읽기/쓰기 성능**: 인덱스 최적화와 도큐먼트 단위 조회로 빠른 처리 가능
    - **애플리케이션 친화적**: JSON 기반 → 웹/앱 데이터와 자연스럽게 매핑 가능
- **단점**
    - **데이터 중복 가능**: 관련 데이터를 도큐먼트에 중첩하면 중복 증가 → 업데이트 시 복잡
    - **복잡한 트랜잭션 처리 어려움**: ACID 트랜잭션 지원 제한적 → 여러 도큐먼트 간 일관성 관리 어려움
    - **조인/연관 관계 제한**: 관계형 DB처럼 자유로운 조인 불가, 복잡한 분석 쿼리 어려움
    - **인덱스 관리 필요**: 잘못된 인덱스 설계 시 검색 성능 저하 가능
    - **데이터 일관성 책임은 애플리케이션에**: 데이터 무결성 기능 제한 → 설계 주의 필요

#### 3️⃣ 그래프 모델 (Graph Model)
- **정의**: 데이터를 노드(개체)와 엣지(관계)로 표현하여, 복잡한 관계와 연결 정보를 직관적·효율적으로 저장·조회
- **장점**
    - **복잡한 관계 표현 용이**: 노드와 엣지를 통해 다대다, 계층, 네트워크 관계 직관적 표현
    - **관계 중심 쿼리 효율적**: 연결 탐색(traversal)이나 경로 탐색이 빠름
    - **유연한 스키마**: 노드/엣지마다 다른 속성 가능 → 구조 변경 자유
    - **실시간 추천/분석에 강점**: 소셜 그래프, 추천 시스템, 사기 탐지 등 복잡한 관계 분석에 유리
    - **연결 중심 데이터 최적화**: RDB에서 조인으로 처리할 복잡한 관계 자연스럽게 모델링 가능
- **단점**
    - **대규모 단순 데이터 처리 비효율**: 단순 테이블 조회, 집계, 정렬 시 RDB나 도큐먼트 DB보다 느릴 수 있음
    - **확장성 고려 필요**: 분산 환경에서 노드/엣지 연결 유지하며 확장 구조 설계 복잡
    - **표준화 부족**: 범용 표준 쿼리 언어 부족 (Cypher, Gremlin 등 별도 언어 필요)
    - **학습 비용**: 기존 RDB 개발자에게 개념과 쿼리 방식 생소
    - **도구 및 생태계 제한적**: 일부 그래프 DB는 에코시스템과 관리 도구 제한적
