## 3. 저장소와 검색 ✅

---

### 💬 인덱스 (Index)
- **정의**: 기본 데이터에 추가된 파생 데이터 구조, 쓰기 효율은 떨어뜨리지만 읽기 효율 향상

---

### 💬 기본키 인덱스 구조 (Primary Index)

#### 1️⃣ 해시 인덱스 (Hash Index)
- 키 → 바이트 오프셋 매핑: 키에 해당하는 바이트 접근 시 즉시 값 조회

#### 2️⃣ LSM 트리 (Log-Structured Merge-Tree)
- **정의**: 백그라운드에서 SS 테이블을 지속적으로 컴팩션
- **배경**
    - 로그 형태 파일 저장소: 모든 변경 사항을 row 단위로 저장, 조회 시 마지막 row 사용
    - 컴팩션: 중복 키 제거, 최신 갱신 값 유지, 세그먼트 단위 병합
    - SS 테이블 & 멤 테이블: key-value 정렬, 멤 테이블 가득 차면 SS 테이블로 flush
    - 블룸 필터: 존재하지 않음을 빠르게 판단, O(k) 시간, 해시 충돌 무시
- **컴팩션 전략**
    - Size-tiered compaction
    - Leveled compaction
- **기본 동작**
    - CREATE: Mem Table 저장 → 가득 차면 SS 테이블 flush
    - READ: Mem Table → Bloom Filter → SS 테이블 블록 단위 조회
- **장점**
    - 쓰기 처리량 높음, SSD 적합, 압축률 좋음, 페이지 단편화 적음
- **단점**
    - 컴팩션이 읽기/쓰기 성능에 영향, 구성 복잡, 세그먼트 많으면 읽기 속도 저하

#### 3️⃣ B 트리 (B-Tree)
- **정의**: 고정 크기 블록에 키 범위와 포인터 저장, leaf 블록에 값 저장
- **기본 동작**
    - CREATE: leaf 블록에 값 추가, 필요 시 상위 블록으로 이동
    - READ: leaf 블록에서 값 조회, log(depth) n
- **최적화**
    - 키 축약, 리프 블록 인접 배치, 포인터 추가, 로그 구조화 개념 차용
- **장점**
    - 데이터 규모 증가에도 읽기 속도 예측 가능, 각 키 색인 한 번만 존재
- **단점**
    - 쓰기 증폭 발생, 물리적 조회 느릴 수 있음

---

### 💬 보조 인덱스 구조 (Secondary Index)

#### 1️⃣ 개요
- **특징**: B트리/LSM트리 모두 사용 가능, 키 중복 발생 가능
- **중복 해결 방법**
    1. row 식별자 목록 저장
    2. 키 값에 row 식별자 추가
- **유형**
    - 클러스터드 인덱스 (Clustered Index): 실제 값 포함, 테이블당 하나
    - 논 클러스터드 인덱스 (Non-clustered Index): 참조 포함, 추가 조회 필요
    - 커버링 인덱스 (Covering Index): 여러 컬럼 포함, 인덱스 내 정보만 조회 가능
    - 인클루디드 인덱스 (Index with Included Column): 특정 컬럼만 포함, B-Tree depth 영향 없음
    - 멀티 컬럼/복합 인덱스: 키 순서 중요, Leftmost Prefix Rule 적용
    - Bitmap/Hash Index: 순서 불필요, 단건 조회 유리, 범위 조회 불리

#### 2️⃣ R 트리 (R-Tree)
- GIS, 2D/3D 공간 정보 저장, 좌표로 트리 영역 표현

#### 3️⃣ 퍼지 색인 (Fuzzy Index)
- 비슷한 단어 검색용, 편집 거리 유지, 유한 상태 오토마톤 트라이 구조 (Lucene)

### 💬 인메모리 데이터베이스
- **정의**: 메모리 내 모든 데이터 저장, 주로 캐시 용도
- **특징**
    - 디스크와 램 가격 차 감소
    - 영속성 위해 디스크 백업 가능
    - 디스크 기반 인덱스로 구현 어려운 구조 지원 (우선순위 큐 등)
    - 안티 캐싱: 메모리 부족 시 디스크 활용

### 💬 트랜잭션

#### 1️⃣ OLTP (OnLine Transaction Processing)
- **특징**: 사용자 입력 기반 Insert/Update, 적은 레코드 조회, 임의 접근, 낮은 지연 시간, 웹/앱 최종 사용자 대상

#### 2️⃣ OLAP (OnLine Analytic Processing)
- **특징**: 비즈니스 인사이트 분석, 대용량 집계, bulk 데이터 로드/이벤트 스트림
- **데이터 웨어하우스**
    - OLTP와 별도, 조회 목적
    - 스타 스키마 (Star Schema)
        - 팩트 테이블(Fact Table): 측정값 저장, 이벤트 기록, 외래키 연결
        - 디멘션 테이블(Dimension Table): 맥락/속성 저장, 중복 허용, SQL 단순
    - 스노우플레이크 스키마 (Snowflake Schema): 일부 디멘션 정규화
    - 칼럼 지향 저장소: 컬럼 단위 저장, 집계 최적화, 압축 효율 높음, 벡터화 처리, LSM 트리 적용
    - 데이터 큐브: 다차원 집계, OLAP 구조
        - 예: Fact(`Sales(amount, product, region, date)`)
            - 3차원 큐브: 제품별, 지역별, 연도별 매출 합계
            - 2차원 큐브: 제품별, 지역별 매출 합계
            - 1차원 큐브: 지역별 매출 합계
    - 구체화 뷰 (Materialized View): 쿼리 결과 물리적 저장, 필요 시 바로 읽기, 주기적 refresh 필요
