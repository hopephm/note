### 🏖️ 개요

---

- 세션 설명

```markdown
**기존 MQTT와 Polling 기반의 알림 시스템의 한계를 넘어, Server-Sent Events(SSE)를 도입해 더 빠르고 효율적인 실시간 알림 인프라를 구축했습니다. 
단순히 기술을 교체하는 것을 넘어, 배달의민족 비즈니스에 맞춰 SSE를 최적화하고 메시지 신뢰성을 확보한 과정의 핵심 기술과 노하우를 공유합니다.**
```

- 키워드

```markdown
- 서비스에 실시간 알림 도입을 고려 중인 분
- Polling 방식의 한계를 느끼고 SSE 등 기술 도입을 검토 중인 분
```

### 🗒️ 노트

---

#### 1️⃣ 개요

- 정의 : 모바일·웹 클라이언트 알림 수신 아키텍처 개선 프로젝트
- 목적
    - MQTT 기반 Zero Payload 구조의 한계를 개선
    - 보안·네트워크·순서보장 문제를 해결하고, 서버 → 클라이언트 단방향 이벤트 전송 구조 확립
    - SSE(Server-Sent Events) 기반으로 알림 안정성과 일관성 확보

#### 2️⃣ 기존 문제

- Zero Payload 구조 한계
    - API 서버에서 직접 데이터 확인 및 비교 후 이벤트 처리
    - 클라이언트 버전에 종속 → 이벤트 정의 변경 시 호환성 문제 발생

- 보안 취약
    - MQTT Broker 접근에 대한 인증 제한 부재
    - Zero Payload 특성상 민감 데이터 노출은 없었으나 접근 통제가 미비

- 네트워크 제약
    - MQTT 표준 포트(1883, 8883)가 방화벽에서 차단되는 사례 존재
    - 대체 polling 로직 필요로 인해 리소스 낭비

- WebView 이슈
    - MQTT 인증서 노출 시 WebView 환경에서 인증서 표시 문제 발생

#### 3️⃣ AWS IoT 도입

- 보안성 향상
    - X.509 인증서 기반 인증 → 개별 토픽 접근 제어
    - 각 클라이언트는 자신의 토픽만 구독 가능

- 메시지 정형화
    - 알림 문구 및 데이터 포맷을 표준화하여 클라이언트 버전에 비종속화

- 잔존 한계
    - 네트워크 방화벽 차단 및 WebView 인증서 노출 문제는 여전히 미해결

#### 4️⃣ Server-Sent Events (SSE) 도입

- 기술 선정 근거
    - AWS IoT: 일부 근본 문제(네트워크, WebView) 해결 불가
    - WebSocket: 인터페이스 재정의 및 양방향 통신으로 복잡성 증가
    - SSE: 기존 서버 → 클라이언트 단방향 구조와 일치, 브라우저·앱 호환성 우수

- SSE 구현 구조
    - 세 가지 접근방식 중 선택:
        - (1) API 기반 세션 유지 → 단순하나 순서보장 불가
        - (2) 브로커 기반 세션 유지 → 순서보장 가능하나 재시작 시 유실 위험
        - (3) 모든 클라이언트 전송 방식(채택)
            - 네트워크 홉 존재하나 유실 없음, 순서보장 확보
            - `Last-Event-Id` 전달로 데이터 유실 복구
            - `commit` 개념 도입: 중요한 메시지는 커밋 확인 후 처리
            - 메시지 중복 세션 방지 로직 추가
            - 클라이언트 polling 로직 제거 → 불필요 요청 감소

#### 5️⃣ 문제점 및 개선

- Back Pressure 문제
    - 베타 환경에서 메시지 수신 불가 현상
    - Kafka `max.poll.interval.ms` 초과로 파티션 재할당 발생
    - Kafka 설정 정상 / 메시지 처리 성능 이상 없음
    - 원인: Coroutine Channel의 기본 버퍼 사이즈 `0` → overflow 시 메시지 drop
    - 해결: 버퍼 사이즈 확장 및 overflow 정책 수정

- Thundering Herd 문제
    - 모든 클라이언트가 동시에 접속 시 CPU 급등 현상
    - 해결: 접속 재시도 시 랜덤 딜레이 부여

- 불필요 네트워크 I/O
    - 모든 메시지를 전송하나, 클라이언트별 처리 가능 범위 상이
    - 해결: 연결 시 처리 가능한 메시지 타입 식별 후 필터링
