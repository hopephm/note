### 🏖️ 개요

---

- 세션 설명

```markdown
배달의민족 앱 내의 이벤트 전송 플랫폼인 LaaS(Logistics as a Service)에서  Kafka 처리량 한계를 겪으면서 파티션을 늘리지 않고도 처리량을 확장할 수 있는 방안을 고민한 경험을 공유합니다. 
이 과정에서 Parallel Consumer 라이브러리를 도입하게 된 배경과 적용 과정, 운영 중 마주쳤던 이슈 및 해결 방안, 그리고 실제 운영 성과를 중심으로 소개합니다.
```

- 키워드

```markdown
- Kafka 파티션 증설은 부담스럽지만, 처리량은 높이고 싶은 백엔드 개발자
- 대규모 트래픽으로 인한 Kafka Consumer Lag 때문에 고민이 깊은 분
- 안정적인 서비스 운영을 위해 더 효율적인 메시지 처리 전략이 궁금한 개발자
- Kafka로 대용량 트래픽 이벤트를 안정적으로 처리하는 서비스 도메인을 맡은 담당자
```

### 🗒️ 노트

---
#### 1️⃣ 개요

- 주문 이벤트를 처리하는 consumer 에서 처리량 이슈 발생
- 메시지 유실과 중복처리, 파티션 증설없이 처리량을 향상시킨 사례

#### 2️⃣ 해결방안

- consumer 스케일 아웃 
  - 파티션 수에 종속된 병렬 처리량으로 인해 무의미
- 메시지 처리 최적화
  - 서로 다른 모든 비즈니스 로직을 최적화 할 수 없음
- 파티션 증설
  - 파티션이 추가되더라도 리밸런싱 전까지는 기존 컨슈머 그룹이 알 수 없음
    - 리밸런싱 default 5분으로 인해 주문이 5분 간 지연될 수 있음
  - auto.offset.reset=latest 옵션으로 인한 메시지 유실 발생 가능성 존재
  - 기존 dead letter 처리 로직에 파티션을 직접 매칭하고 있어 이슈 존재

#### 3️⃣ parallel consumer

- 특징
  - 파티션 수에 종속된 메시지 처리를 기술적으로 병렬 처리
  - offset map을 통해 완료/미완료 오프셋을 구분, 완료된 가장 마지막 offset을 커밋
    - offset map은 메시지를 가져오거나 커밋할 때 메타 데이터에 포함됨.
    - offset map에만 완료로 기록되고 커밋되지 않았더라도 재처리 되지 않음 
  - 메시지 처리 오류시, retry 별도 개발 필요
  - CPU 제약은 여전히 동일하기 때문에 IO가 큰 작업에서 특히 유효
- 비교
  - spring kafka: 한 파티션 당 하나의 컨슈머에서 메시지 처리
  - spring kafka batch consumer: 한 파티션당 하나의 컨슈머에서 메시지를 청크로 가져와 처리
  - parallel consumer: 한 파티션에서 여러 메시지를 병렬로 컨슘
