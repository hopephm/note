### 🏖️ 개요

---

- 세션 설명

```markdown
BROS는 10년 가까이 유지·보수되어 온 배달 처리 시스템입니다. 배달(OD, Own Delivery) 건수가 계속 증가함에 따라 시스템 안정성과 개발 생산성을 높이기 위해 ‘baeminz 도메인 정리’ 프로젝트를 진행했고, 이를 통해 얻은 성과와 경험을 공유합니다. 현 시스템의 문제를 해결하기 위해 어떤 전략을 세웠는지, 기존과 새로운 아키텍처는 어떻게 달라졌는지, 그리고 고민 끝에 도달한 결론과 다양한 안정성 장치들을 소개합니다. 프로젝트 완료 후 얻은 성과와 향후 개선 방향도 함께 나눕니다.
```

- 키워드

```markdown
- 레거시 시스템을 다루고 있거나, 운영 중인 서비스를 안정적으로 리팩토링하는 업무에 관심 있는 분
```

### 🗒️ 노트

---

1️⃣ 개요

- 정의 : 거대하고 오래된 시스템을 안정적으로 리팩토링하는 프로젝트
- 대상 : 배민 라이더 시스템 및 자체 배달 서비스 지원 시스템
- 목적 : 개발 생산성 향상과 시스템 안정성 확보

2️⃣ 기존 문제

- 라이더, 관리자/상담사, 시스템
    - 모놀리딕 서비스
        - 대부분의 도메인 포함, DB 부하 발생 용이
    - 멀티모듈 프로젝트임에도 공통 모듈에 여러 팀 commit → R&R 문제 발생
    - 과도한 팀간 커뮤니케이션 비용
- 시스템 구조
    - 이벤트 기반이나 기능 간 N:M 관계 → 높은 비용 발생
- 문제 요약
    - 모놀리딕 구조 → DB 성능 확보 필요
    - R&R 불명확
    - 코드 복잡도 높음

3️⃣ 유지보수성 개선

- 목적
    - 개발 생산성 향상
    - 시스템 안정성 향상
- 방향
    - 공통 모듈 의존성 제거
    - 라이더 팀 도메인을 별도 시스템으로 분리
- 전략
    - 공통 모듈 도메인 기능 분리 → 배달팀 / 라이더팀 / 기타
- 개선
    - 사용 여부 및 대체재 확인
    - 후 처리 로직을 메소드 콜 형태로 단순화 / 트랜잭션 분리
    - 공통 모듈 내 서비스별 분기 단순화
- 요약 : 의존성 분리

4️⃣ 성능 개선

- 배달 진행 목록 트랜잭션 최소화
- Reader DB 활용, 트랜잭션 범위 최소화
- Response 경량화
- 미사용 기능 제거

5️⃣ 성과

- 복잡도 감소 : 코드 라인 수, 순환 복잡도, 인지 복잡도 개선
- R&R 명확화 : 공통 모듈 분리
- API Response 및 Latency 경량화
- DB 부하 피크타임 기준 7% 감소
- Reader DB 부하 증가 → 트랜잭션 분리로 인한 영향
- 프로젝트 진행 중 장애 없음

6️⃣ 안정적 전환 요인

- Feature flag 강제화(A/B Test)
    - 0% 배포 후 점진적 전환 → 적은 트래픽 지표 확인 후 완전 전환
    - 반복 호출 시 캐시 적용
    - 다른 서버 처리 시 Kafka 메시지 내 flag 추가
- JSON diff Logger
    - AS-IS 호출 시 TO-BE 병행 호출 후 차이 비교
- 보이스카웃 규칙
    - 코드 수정 발생 시 테스트 코드 추가
- 지속적 의사결정
    - 기능별 역할과 컨벤션 정의
    - 물리적 범위 제한 → 프로젝트 중단 방지 고려
