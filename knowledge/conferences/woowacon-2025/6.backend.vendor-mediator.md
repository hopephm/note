### 🏖️ 개요

---

- 세션 설명

```markdown
**공통시스템개발팀의 메시지/맵 미디에이터는 서비스 특성상 외부 벤더와 연동되며, 이에 따라 안정성·성능·비용이 크게 영향을 받습니다. 이를 개선하기 위해 미디에이터 시스템을 활용해 장애 대응, 라우팅, 데이터 통합, 사용량 추적 등 다양한 기능을 구축한 경험을 소개합니다. 장애 발생 지점별 자동 재처리와 수동 트래픽 전환, 메시지·맵 호출 특성에 따른 대응 방식을 마련했으며, 외부 설정 기반의 동적 라우팅과 Kafka 커넥터·CDC·ElasticSearch를 통한 데이터 통합, 대시보드 자동화를 통해 운영 효율을 높였습니다. 마지막으로 이러한 성과와 함께 앞으로 시도해 보고 싶은 방향도 공유합니다.**
```

- 키워드

```markdown
- 다양한 외부 벤더를 연동하는 시스템을 개발하는 개발자
- Kafka/Webflux 등을 활용한 비동기 시스템을 다루는 백엔드 개발자
```

### 🗒 노트

---
1️⃣ 개요

- 정의 : 여러 벤더 및 시스템 요청을 중재하고 트래픽 분배, 장애 대응, 데이터 통합, 비용 관리를 수행하는 미디에이터 시스템
- 대상 : 지도 서비스, 메시지/푸시 알림 서비스

2️⃣ 미디에이터 기능

- 목적
    - 다양한 벤더의 요청 통합
    - 중복 기능 제거 및 비용 효율화
- 사례
    - 지도 미디에이터 : 실 거리 조회, 주소 ↔ 좌표 변환, 장소 검색(POI)
    - 메시지 미디에이터 : 모바일 알람, Push, Poll

- 벤더 게이트웨이 연동
    - 단일 벤더
        - 장점 : 중복 비효율 감소
        - 단점 : 벤더 장애 시 전체 장애, 성능 벤더 종속, 비용 협상력 저하
    - 다중 벤더
        - 장점 : 장애 대응 가능, 비용 협상력 강화
        - 단점 : 트래픽 분배 필요, 장애 발생 시 대응 필요, 데이터 통합 필요, 비용 관리 필요
        - 결론 : 상황에 맞는 벤더 선택 필요 (트래픽, 장애 대응, 데이터 통합, 비용 포함)

3️⃣ 주요 기능

- 라우팅 기능
    - 목적 : 성능, 비용, 특성 기반 트래픽 가중치 분배
    - 사례
        - 맵 미디에이터 : 라우팅 비율 DB 저장, 벤더 장애/초과 시 DB 값과 별개 계산
        - 메시지 미디에이터 : 벤더 트래픽 초과 시 장애 발생, 상황별 비율 사전 정의

- 장애 대응 기능
    - 목적 : 장애 감지 및 준 실시간 트래픽 재분배
    - 맵 미디에이터
        - 실시간 응답 구조, 오류/장애 즉시 식별
        - 특정 벤더 실패 시 즉각 다른 벤더로 전환
        - 오픈소스 엔진 및 circuit breaker로 자동 트래픽 전환
    - 메시지 미디에이터
        - 실시간 응답 아님 → 벤더 → 중계 → 단말 도달 후 오류 확인
        - 장애 대응
            - 케이스1 : 요청 시 벤더 오류 → 다른 벤더로 즉각 전환, 전체 장애 시 Redis 적재 후 재처리
            - 케이스2 : 중계 전송 오류 → 벤더 실패 감지 시스템 모니터링 → 다른 벤더 전환

- 데이터 통합 기능
    - 목적 : 벤더별 다른 응답 포맷 통합
    - 구현 : 각 벤더 응답을 공통 포맷으로 변환 후 통합

- 비용 관리 기능
    - 사용량 추적
        - 요청 데이터 로깅 → 집계 및 정산 활용
    - 비용 최적화
        - 벤더별 요금 체계 반영 → Rate limiter 적용

### ⏰ 후기

---

- 다중 벤더에 대한 미디에이터를 통해 장애 대응 및 비용 절감한 사례
- 벤더 요청량 로깅을 통한 트래픽 제어 / 비용 절감 개념
- 이벤트 요청 형태의 벤더 활용 및 통합 사례
